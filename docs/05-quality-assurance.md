# QA и критерии приёмки

Цель тест-дизайна — проверять не только «счастливый путь», но и целостность состояния, границы доступа и поведение при повторных командах.

## Риск-ориентированная матрица

| ID | Сценарий | Ожидаемый результат | Риск |
|---|---|---|---|
| TC-01 | Дважды отправить одну активацию с одним ключом | Создано одно прохождение, списание не дублируется | Критический |
| TC-02 | Сохранить устаревшую ревизию черновика | Новый текст не перезаписан | Высокий |
| TC-03 | Повторить тот же запрос сдачи | Не создаётся новая попытка | Высокий |
| TC-04 | Переиспользовать ключ сдачи с другим содержимым | Конфликт, а не молчаливое принятие | Высокий |
| TC-05 | Открыть чужое прохождение | Отказ в доступе | Критический |
| TC-06 | Запросить материалы будущего задания | Закрытый материал не раскрывается | Высокий |
| TC-07 | Остановить прохождение на оценке | Состояние остаётся согласованным; нет самопроизвольного продвижения | Высокий |
| TC-08 | Получить неопределённый результат AI | Нет автоматического PASS без достаточных оснований | Критический |
| TC-09 | Завершить последнюю задачу | Прохождение переходит в COMPLETED ровно один раз | Высокий |
| TC-10 | Открыть завершённую пробу | История доступна на чтение, редактирование запрещено | Средний |

Это **материалы для демонстрации тест-дизайна**, а не протокол нового запуска всех десяти тестов в этом репозитории.

## Пример тест-кейса с шагами

**TC-02 — конфликт версий черновика**

- **Предусловия:** есть текущая редактируемая задача; два клиента получили ревизию `r`.
- **Шаг 1:** первый клиент сохраняет изменение с `r`, сервер выдаёт `r+1`.
- **Шаг 2:** второй клиент пытается сохранить другой текст с устаревшей `r`.
- **Ожидается:** отказ/конфликт версии; документ из шага 1 сохранён; возможен безопасный повтор после получения актуальной ревизии.
- **Критерий дефекта:** сервер без предупреждения принимает старую запись и теряет первое изменение.

## Уровни проверки

1. **Статические проверки:** typecheck, lint, сборка.
2. **Unit:** бизнес-инварианты, валидаторы, расчёты, состояния.
3. **Integration:** API + PostgreSQL, внешние границы, идемпотентность.
4. **Синтетические E2E:** полное прохождение заданий на тестовых данных.
5. **Внешняя содержательная валидация:** эксперты профессий, реальные пользователи, качество AI-оценок.

В приватном проекте имеются различные интеграционные тесты, в том числе для runtime, отдельных профессиональных кейсов, безопасности и аналитики. **Факт их наличия не равен свежему успешному запуску**. Этот публичный репозиторий не содержит CI-отчёта, подтверждающего текущий релиз.

## Разделение подтверждений

| Что подтверждает | Чего не подтверждает |
|---|---|
| Успешный unit/integration test | Готовность к использованию в реальной среде |
| Успешный синтетический end-to-end | Удовлетворённость реальных пользователей |
| Успешная проверка корректности SQL | Качество бизнес-выводов |
| Реальный production smoke | Отсутствие всех возможных дефектов |

**Вывод:** приёмка требует сочетания технических, продуктовых и эксплуатационных свидетельств.
