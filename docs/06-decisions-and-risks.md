# Решения и риски

## Изменение правила повторной активации

**Проблема.** Идемпотентность защищает повтор одной команды. Вторая вкладка или повторное нажатие могут создать новую команду с другим ключом. Тогда пользователь рискует получить лишнее прохождение и израсходовать право доступа.

**Решение.** В сентябре 2026 года правило закрепили на уровне версии ПРОБЫ. Повторная активация открывает действующее прохождение этой версии. Если оно приостановлено, оно остаётся на паузе до явного возобновления. Для завершённой версии допускается новое прохождение при выполнении условий активации. Выбор ограничивает число параллельных прохождений одной версии и сохраняет возможность перепройти её после завершения.

| Область | Что меняется и как принять |
|---|---|
| Бизнес-правило | Новая команда может открыть старое прохождение без расхода. При двух активных прохождениях повторное открытие существующего сохраняет прежнее состояние |
| API и интерфейс | Ответ активации может содержать существующий идентификатор. Web использует серверный результат для навигации. Пауза и возобновление остаются явными действиями |
| Транзакция | Поиск действующего прохождения, контроль слотов и возможное списание выполняются под одной блокировкой пользователя. Два разных ключа не создают два активных прохождения одной версии |
| История | Изменение правила само по себе не удаляет и не объединяет исторические прохождения. Для старых данных важны сохранность черновиков и воспроизводимость расчётов |
| Регрессия | Проверить параллельные и последовательные повторы, отмену, возобновление при занятом слоте и повтор после завершения. [TC-01 и TC-02](05-quality-assurance.md#трассировка-требований) |

Уникальность по ключу команды сохраняется для сетевых повторов. Уникальность действующего прохождения задаёт самостоятельное правило продукта и проверяется по пользователю и версии.

## Другие решения

| Решение | Причина | Компромисс |
|---|---|---|
| Линейная последовательность вместо календарной модели | Пользователь продолжает после принятия работы, без привязки к дате | Ветвящиеся траектории потребуют отдельной модели |
| Новая версия задания при изменении содержания | Ранее начатые прохождения остаются воспроизводимыми | Растут объём хранения и число комбинаций для регрессии |
| Формальные проверки перед содержательной оценкой | Обязательные условия имеют проверяемые причины отказа | Для каждого формального условия нужен свой валидатор |
| Модульный монолит с отдельными worker и runner | Транзакционные правила остаются в API, а фоновые операции и выполнение кода получают свои границы | Согласованность статусов и диагностируемость фоновых задач требуют отдельных проверок |

## Приоритеты при выпуске

| Приоритет | Риск | Мера и проверяемое условие |
|---|---|---|
| Критический | Двойной расход права или чужой доступ к работе | Транзакционные ограничения, тест конкурентной активации и отрицательные проверки авторизации |
| Высокий | Ошибка или недоступность оценщика | Сохранить версию работы, направить неопределённый результат на разбор и проверять качество на размеченных примерах |
| Высокий | Новая версия портит существующие прохождения | Сохранять закреплённые версии, проверять свежие и ранее начатые сценарии перед выпуском |
| Средний | Оценка конверсии по незрелым когортам | Зафиксировать окно наблюдения, версию ПРОБЫ и правила исключения тестовых данных |
