# Архитектурные решения, альтернативы и риски

Краткая выборка из логики проектирования ПРОБЫ. Риски здесь — демонстрация аналитического мышления, а не раскрытие внутренних инцидентов или конфигурации защиты.

## Решения и альтернативы

| Вопрос | Выбрано | Альтернатива | Компромисс |
|---|---|---|---|
| Координация backend | Модульный монолит | Микросервисы | Меньше операционных затрат, но выше связанность модулей |
| Модель прохождения | Линейный task pool | Граф с ветвлениями | Проще инварианты, меньше гибкость |
| История результатов | Неизменяемые сдачи и версии | Перезапись последнего файла | Выше затраты на хранение, но лучше аудит |
| Источник состояния | PostgreSQL / server authority | Локальный прогресс браузера | Больше серверных операций, но устойчивее контроль |
| Проверка задач | Формальные валидаторы + содержательная оценка | Только LLM | Больше трудозатраты на валидаторы, но меньше произвол |
| Запуск пользовательского кода | Отдельная изолированная среда | Исполнение внутри API | Сложнее инфраструктура, зато меньше риск для API |

## Реестр ключевых рисков

| ID | Риск | Влияние | Мера контроля |
|---|---|---|---|
| R-01 | Оценщик неверно принимает или отвергает работу | Высокое | Версионированные критерии, проверка свидетельств, ручной пересмотр |
| R-02 | Повтор запроса создаёт двойную активацию / сдачу | Высокое | Ключи идемпотентности, уникальные ограничения и транзакции |
| R-03 | Изменение задания ломает старые прохождения | Высокое | Иммутабельные версии и закрепление версии за run |
| R-04 | Доступ к чужой работе или артефакту | Критическое | Контроль владения и отрицательные тесты |
| R-05 | Выпуск функции без содержательной проверки | Высокое | Независимые quality/release gates и разделение статусов |
| R-06 | Ранние KPI дают ложную картину конверсии | Среднее | Когорты с единым окном наблюдения и фильтр тестовых аккаунтов |
| R-07 | Расходы на AI превышают вклад платящих пользователей | Высокое | Учёт себестоимости оценки, лимиты, анализ unit economics |

## Риск-ориентированный приоритет

1. Сначала целостность и контроль доступа — потенциально необратимые ошибки.
2. Затем качество проверки и возможность корректировки результата.
3. Затем надёжность выпуска новых профессий и мониторинг.
4. Только после базовой надёжности — ускорение роста и оптимизация конверсии.

## Пример анализа изменения

**Запрос:** поддержать новую профессию с набором задач, для которых требуются новые инструменты.

- **Impact:** контент и рубрики, API-контракты, UI-примитивы, evaluator, runner (при необходимости), тесты и выпускная процедура.
- **Риск:** существующие задачи/проверки могут менять поведение из-за общего кода.
- **Условие приёмки:** новый кейс проходит изолированные тесты, а исторические версии — регрессию.
- **Условие публичного выпуска:** помимо engineering PASS нужны необходимые продуктовые, качественные и эксплуатационные подтверждения.

Это пример методики change impact analysis, а не отчёт о выпуске конкретной новой профессии.
